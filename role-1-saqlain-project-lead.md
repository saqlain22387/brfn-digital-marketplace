## You must be able to explain

- **Why Scrum-style sprints:** the module is organised in sprints with fixed review dates; a Kanban board inside each sprint shows work moving.
- **Why the board is in the repo:** its history is versioned with the work, so changes can be seen next to the commits.
- **MoSCoW:** Must = needed to pass the sprint review; Should = needed for the higher bands; Could = polish.
- **Definition of Done:** committed, reviewed by the review partner, traced to a stakeholder goal, runs (for Camunda items), board updated, contribution logged.
